## Why it exists

The replica renders browser defaults for controls that cannot be styled: a native `select`'s option list, the date picker, the file input's button, the checkbox and radio glyphs, `details` disclosure. Klent's own words on 2026-09-03: "i want custom components. i dont want browser defaults. like for instance, dropdown options are default browser. i dont like that."

Separately, on 2026-09-04: "i can see multiple fields and buttons that have different heights." Measured against the stylesheet, nothing declares a control height. `.btn` is `padding: 9px 18px` at 14px with `line-height: 1.25`, `.btn-sm` is `6px 8px` at 13px, and `.field input`, `.field select`, `.field textarea` and `.input` are `8px 10px` at 14px with **no line-height at all**, so each control's height is whatever padding, border and an inherited line-height happen to produce. That is V9's finding and W1's job.

## The items

- **W1 Control geometry first**, because it is the visible complaint and it touches every screen. Land V9's height scale as tokens, apply it by declaring height with `line-height: 1` and centred content rather than deriving height from font size, fix label-to-control alignment, toolbar gaps and table row height against the controls inside them, and ship the build guard V9.5 specified so the next hand-tuned padding cannot reintroduce the drift.
- **W2 The select and the combobox.** The single case Klent named. A listbox that can be styled, with the WAI-ARIA keyboard contract: type-ahead, Home and End, arrow navigation, Escape to close, Enter to commit, and the `aria-activedescendant` or focus-follows model V7 chose.
- **W3 The date input.** The native picker cannot be styled and differs per browser. Keep the text field parseable and typeable; the calendar is an addition, not a replacement for typing.
- **W4 Checkbox and radio glyphs**, including the indeterminate state the bulk-select header row needs, with the native input kept for accessibility and the glyph drawn over it.
- **W5 The file input**, whose button text and appearance are browser-decided today.
- **W6 `details` disclosure**, 6 uses, so the accordion mechanics match `RecordSection` rather than the browser's.
- **W7 Focus and scrollbar treatment**, the two remaining browser decisions that show on every screen.
- **W8 Everything else in V8's priority order**, driven by which controls appear on the screens people actually use rather than by how interesting they are.
- **W9 The remaining task list.** `verify-zoho-sample.mjs` once its three `ZOHO_` variables exist, reported as not run rather than green if they do not. The candidate list re-measured at offsets 0, 20 and 2000 once the develop Supabase project exists, since `effective_cache_size` here is a stock 128 MB and Supabase tunes it per compute size. The two decisions that are Klent's, the 76.5 MiB attachment against the bucket's 25 MiB `file_size_limit` and whether `can_read_person` should be deleted, acted on if he has answered and surfaced again if not.
- **W10 Prove it visually.** Re-capture every state V2 screenshotted and diff against that corpus, so an intended change is visible and an unintended one fails. A component is not done because it looks right in one state.

## How each component ships

Complete or not at all. The props API, keyboard map and ARIA roles V7 specified, the WAI-ARIA Authoring Practices contract read from source with its URL cited, design tokens rather than hard-coded values, and the motion budget `check-motion.mjs` enforces. **A control that looks right and cannot be driven from the keyboard is not done.** Fidelity to Taleo still governs, so a control that diverges from Taleo needs a stated reason, not a preference.

Each component also ships its tests: the keyboard contract, the ARIA roles, every state V1 inventoried, and the empty and error cases. Tests leave no rows, storage objects or queue entries behind and check the error on every teardown call.
