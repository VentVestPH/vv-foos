## Why it exists

The replica renders browser defaults for controls that cannot be styled: a native `select`'s option list, the date picker, the file input's button, the checkbox and radio glyphs, `details` disclosure. Klent's own words on 2026-09-03: "i want custom components. i dont want browser defaults. like for instance, dropdown options are default browser. i dont like that."

Separately, on 2026-09-04: "i can see multiple fields and buttons that have different heights." Measured against the stylesheet, nothing declares a control height. `.btn` is `padding: 9px 18px` at 14px with `line-height: 1.25`, `.btn-sm` is `6px 8px` at 13px, and `.field input`, `.field select`, `.field textarea` and `.input` are `8px 10px` at 14px with **no line-height at all**, so each control's height is whatever padding, border and an inherited line-height happen to produce. That is V9's finding and W1's job.

The two decisions that are Klent's, the 76.5 MiB attachment against the bucket's 25 MiB `file_size_limit` and whether `can_read_person` should be deleted, acted on if he has answered and surfaced again if not.
- **W10 Density and wasted space, from V13.** Klent on 2026-09-04: "taleo is still the standard, but i can see ugly designs with huge spaces and what not. i want that change." **Taleo stays the standard, and Taleo is dense**, so a screen that sprawls is usually a departure from it rather than fidelity to it, and tightening it is the fidelity move as well as the usability one. Land V13's target heights: cut the vertical space that carries no content, make label-to-control and control-to-control gaps consistent, and bring table row height into line with the controls inside the row. The record page is the known case at 5,979px in a 572px window, 10.5 screens, of which History Log / Timeline alone is 2,812px and 563 of 894 nodes. Where genuine Taleo fidelity is what makes a screen harder to use, that is a recommendation for Klent, not a change to make alone.
- **W13 Textarea resize, vertical only.** Klent, 2026-09-04: "the text-area being horizontally adjustable. it should only be vertical, not horizontal." A textarea's default is `resize: both`, so dragging one wider breaks the column it sits in. `resize: vertical` is already declared in four module stylesheets, `settings.css`, `recruit.css`, `sales.css` and `intake.css`, but textareas appear in **13 files**, so the declarations do not obviously cover them all. The measurement records the computed `resize` of every textarea on every screen, and W13 fixes the ones that come back `both` by declaring it once on the shared control rather than a fifth time per module. `none` is not the answer: taking away vertical resize removes something useful.
- **W14 Every button shows a pointer cursor.** Klent, same message: "all buttons should have hover cursor pointer." `cursor: pointer` is declared in several places already, `.btn`, `.link-btn`, the nav tabs, the utility icons, the section headers and the pager controls, so the gap is in whichever button-like control was styled without it. The measurement records the computed `cursor` of every button, link-button and `.btn` on every screen, and W14 fixes the ones that are not `pointer`, excluding `default` on a disabled control, which is correct behaviour rather than a defect.
- **W15 The focus ring is invisible on the two dark shell surfaces, and the contrast guard does not catch it.** Measured, not observed: the ring is `outline: 2px solid var(--fo-primary)` with `outline-offset: 1px`, which is `#3679b5`. **Corrected on 2026-09-04, from four surfaces to two.** The offset places the ring outside the element's border box, so the surface it must contrast against is the nearest painted ancestor, not the control. On that basis it fails on `--fo-nav` `#427d98` at **1.013:1**, behind all 14 primary nav tabs, and on `--fo-sidebar-header` `#577995` at **1.003:1**, behind the sidebar panel headers, where WCAG 1.4.11 requires 3:1. `--fo-logout` and `--fo-primary-hover` were wrongly listed: Logout's ring lands on the white utility header and a hovered primary button's on the white page surface, both at 4.606:1, both passing. **`scripts/check-contrast.mjs` misses the real failures because line 20 checks `['focus ring', '--fo-primary', '--fo-surface', 3.0]` only**, the one pair that passes, so the gate is green while the ring is invisible on the navigation. W15 fixes the ring, most likely with a light inner or outer companion stroke so it reads on both dark and light grounds, and extends the guard to check the ring against every background a focusable control can actually sit on, taking the painted-ancestor list from the V9 measurement rather than from the token file.
- **W16 Row-level controls need row identity in their accessible name.** V6 row 23, measured: on the candidate list **100 of 163 interactive controls, 61%, share a name with nineteen others**. `Table.tsx:268` labels every row checkbox `Select row`, `StarGrade.tsx:31` labels every star group `Star grade` and names each star from a `title` attribute alone, and `ApplicationPipeline.tsx:428` gives 21 controls the same `Add to shortlist`. Give each the row's own subject, so a screen-reader user hears which candidate they are selecting or grading. This compounds W4: with the header checkbox reporting the wrong state and no row distinguishable by name, the selection mechanism is unusable non-visually, so W4 and W16 should land together.
- **W17 One unlabelled control, and one weak-source name pattern.** `modules/intake/SheetImportPage.tsx:236` is the only `<Select` of 54 that omits a `label`, so its accessible name is its placeholder option. Separately, `StarGrade` names each star from `title`, which the accessible-name computation treats as the weakest source after `placeholder`. Both are one-line fixes and both were found by counting call sites rather than by looking, and the counting also acquitted the other 148 field call sites, so W17 is deliberately small rather than a sweep.
- **W18 One dialog, replacing five, that actually traps and restores focus.** V6 row 26. `IdleSignOut`, `Placeholder`, `recruit/Dialog`, `sales/Modal` and `intake/Drawer` all declare `aria-modal="true"` and not one traps focus or returns it to the trigger; grep for `activeElement`, `trapFocus` or `focusTrap` across `app/src` returns nothing, and three of the five have no `autoFocus` either. The APG warns that `aria-modal="true"` should be set only when application code prevents external interaction, because misuse "can prevent users of some assistive technologies from perceiving content outside the dialog", so the attribute currently asserts an inertness that does not exist. Build one dialog in `components/ui/` with focus entry, a Tab cycle, Escape and focus return, and retire the three near-identical module copies at 43, 40 and 39 lines. They exist because ESLint forbids cross-module imports and `components/ui/` holds no dialog, so the shared component is the fix for the duplication as well as the behaviour.

- **W11 Prove it as the user, not as the author.** Re-walk V10's task list after each change: move a candidate through the stages, add one and find it again, search for nothing, fix a validation error, export a filtered list. Report the click, field and page-load deltas against V10's baseline. A component that did not make its task easier has not earned its commit.
- **W12 Prove it visually.** Re-capture every state V2 screenshotted and diff against that corpus, so an intended change is visible and an unintended one fails. A component is not done because it looks right in one state.

## How each component ships

Complete or not at all. The props API, keyboard map and ARIA roles V7 specified, the WAI-ARIA Authoring Practices contract read from source with its URL cited, design tokens rather than hard-coded values, and the motion budget `check-motion.mjs` enforces. **A control that looks right and cannot be driven from the keyboard is not done.** Fidelity to Taleo still governs, so a control that diverges from Taleo needs a stated reason, not a preference.

Each component also ships its tests: the keyboard contract, the ARIA roles, every state V1 inventoried, and the empty and error cases. Tests leave no rows, storage objects or queue entries behind and check the error on every teardown call.

## How it runs: five passes per component, not one

A component is not finished when it renders. Each one goes through the same five passes, and each pass reports what it caught:

1. **Build.** The props API, keyboard map, ARIA roles, tokens and motion budget V7 specified.
2. **Keyboard and screen reader.** Drive it with the keyboard alone against the WAI-ARIA contract, cited by URL. A control that looks right and cannot be driven from the keyboard is not done.
3. **Every state.** All of them from V1's inventory: default, hover, focus-visible, active, disabled, error, loading, empty, populated, long value, overflow. Then the visual diff against V2's corpus.
4. **In context.** The same control on every screen that uses it, because a control that is right in isolation and wrong in a toolbar is wrong.
5. **As the user.** Re-walk V10's task list and report the click and page-load deltas against its baseline.

Then a sixth pass over the whole workstream at the end: the full gate 5 to 10 times, the complete corpus re-diffed, and every task re-walked, because per-component passes miss what only shows when everything has moved.
