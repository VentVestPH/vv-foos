## V12: the severity scale

Severity is what the defect costs the person doing the work, not how hard it is to fix. "Good enough" is not a severity.

| Level | Meaning |
| :---- | :---- |
| **Blocks** | the user cannot complete the task, or completes it wrongly without knowing |
| **Costs** | the task completes, but slower, or with a risk of error the user has to absorb |
| **Degrades** | it works and is noticeably inconsistent or unfinished in a way a user remarks on |
| **Cosmetic** | visible on inspection, not in use |

The priority order in V8 follows this ranking. Where two rows share a severity, the tie-break is how many users meet it, measured by how many screens the component appears on.

## What was checked and found correct

An audit that only lists defects is not an audit. Three things were suspected from the corpus, checked against source, and found to be right, and each was written up as a finding first.

**`aria-sort` is implemented correctly.** `Table.tsx:217` sets `ascending` or `descending` on the active column and leaves it off the others, which is right. The header's keyboard access is not, and that is row 25; the announcement is.

**`aria-modal` is present on every dialog.** All five set it. That is the correct attribute, and row 26 is about the behaviour it asserts being absent, not the attribute being missing.

**`autocomplete` is correct by omission, and this one matters.** Only two `autoComplete` attributes exist in the whole application, `email` and `current-password`, both on `LoginPage`. That looked like 93 missing attributes against [WCAG 1.3.5 Identify Input Purpose](https://www.w3.org/WAI/WCAG22/Understanding/identify-input-purpose.html). It is not: 1.3.5 covers fields collecting information **about the user**, and in an ATS every other field collects candidate, company or requisition data. Putting `autocomplete` on those would be actively wrong, since browser autofill would offer the recruiter's own name and address for a candidate's record. The two that exist are exactly the two that should. No change, and no W item.

**`prefers-reduced-motion` is handled**, at `motion.css:267`, and `scripts/check-motion.mjs` guards it in the gate. Checked because a workstream adding transitions to a select, a date picker and an accordion needs to know the reduced-motion path already exists rather than discovering it later.

**`lang="en"` is set** on the root element in `index.html`.

**Every field is properly labelled.** The corpus showed 61 desktop controls whose accessible name was nothing but their kind, which read as 61 unlabelled inputs. It is a harness artefact: my name resolution was `aria-label`, then `title`, then `placeholder`, then `innerText`, and it never consulted `<label for>` or `aria-labelledby`, which the accessible-name computation puts *first*. `Input.tsx` and `Select.tsx` both render `<label className="field-label" htmlFor={id}>` whenever a `label` prop is passed. Counting the call sites: **all 95 `<Input` pass a label, and 53 of 54 `<Select` do.** The single exception is `modules/intake/SheetImportPage.tsx:236`, whose only accessible name is its placeholder option. So this is one unlabelled control in the product, not 61, and it is a one-line fix rather than a pattern.

**The `Select…` duplicates are the same artefact.** Three controls on the requisition form appeared to share the name `Select…`. They have proper labels; my chain preferred the placeholder over the associated label. Not a finding.

**The pager conforms to WCAG 2.5.8.** See the note below on row 2.

**On row 2's severity, raised and then put back on 2026-09-04.** I raised it from Degrades to Costs on the grounds that the pager's 22px arrows fail the WCAG 2.5.8 AA target size on every list in the product. Then I computed the spacing exception instead of asserting it: `min-width: 26px` plus a 4px gap puts the arrow centres 30px apart, the exception needs 24px, and a single row has no vertically adjacent target. **The pager conforms.** So the reason for the raise evaporated and the severity goes back to Degrades.

What remains true is that 154 of 1,066 button captures are under 24px. Whether any of them fails 2.5.8 outright rather than conforming by spacing is now computed rather than argued: `analyse.mjs` takes the measured box of every sub-24px control, centres a 24px circle on it, and finds the nearest other target's centre on the same screen and viewport. Until that runs, the honest statement is that the count of controls below the AA size is known and the count of actual 2.5.8 failures is not, and it may well be zero.

This is worth leaving in rather than tidying, because raising a severity on an accessibility claim I had not tested is the same mistake as the four surfaces in row 11, one step further along: there I reasoned about the wrong element, here I reasoned about the threshold and skipped the exception written into the same success criterion.
