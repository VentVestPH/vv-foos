## Architecture

### Security lives in the database

RLS is enabled on every table, deny-by-default. Role comes from `staff.role` looked up via `auth.uid()` by `get_my_role()` (security definer), never from a client parameter. Route guards in `App.tsx` and role filters in `navConfig.ts` are UI courtesy only; adding a role to a guard grants nothing that Postgres does not already allow, and removing one hides nothing that RLS still exposes.

`staff.id` must equal the matching `auth.users.id`. There is no hard FK (so migrations stay runnable on plain Postgres). **Corrected 2026-09-09: there is no signup hook.** No trigger exists on `auth.users`, in any of the 58 migrations or on the live project, so nothing reconciles the two ids automatically. Creating an account means writing both rows from one id, which is what `scripts/add-local-staff.sql` does; it is local-only, so a hosted account needs the same SQL run by hand. Never use the dashboard's Add user button: it mints a random id and creates no `staff` row, so the account signs in and `get_my_role()` returns null, which RLS reads as no access. Repointing an existing `staff.id` is not an option either: 19 foreign keys reference it and none is `ON UPDATE CASCADE`, `staff_email_key` forbids a second row per person, and 42 policy clauses compare ownership to `auth.uid()` directly. For Google sign-in, pre-create the `auth.users` row at the staff id with `email_confirmed_at` set and no password; GoTrue then attaches the Google identity to that user instead of creating a new one. Verified on the live project on 2026-09-09: the user row was written at 02:25:11 and the `google` identity landed on the same id at 02:25:35, leaving `users_without_staff_row` at 0.

### Triggers own the derived writes

Stage and status changes are plain `UPDATE`s on `applications`, `requisitions`, `candidate_profiles`, `deals`, `tickets`. Migration 10's triggers then write the `status_change` row in `activities`, the `audit_log` row, and the `events_outbox` event, and maintain `stage_changed_at` / `hired_at`. **Never write `activities` status_change rows, `audit_log`, or `events_outbox` from application code.**

`display_code` (`REQ-`, `APP-`, `DEAL-`, `TKT-`) is issued by a Postgres sequence. Leave it out of every insert.

Zoho exports come in two dialects and `parseZohoTimestamp` handles both: Recruit writes `MM/DD/YYYY hh:mm AM/PM`, CRM writes `YYYY-MM-DD HH:MM:SS`. `Initial Date` has no year and three shapes (`M/DD`, `DD-Mon`, `Mon-DD`); `parsePartialDate` borrows the year from the row's own `Created Time`. An imported attachment path starts with `zoho-import/pending/` until its bytes arrive, and `lib/attachments.ts` is what the UI uses to tell that apart from a real file.

`events_outbox` rows are `(event_name, aggregate_id, payload, created_at, processed_at)`, with null `processed_at` meaning pending. Edge Functions consume them with the service role; the frontend subscribes to them via Realtime (`HiredPromotionListener.tsx` is the canonical example). `tests/EVENT_PIPELINE.md` maps all 10 events to their consuming UI effect.

### Migrations and generated types

`supabase/migrations/*.sql` apply lexically, one concern per file; README.md tabulates 01 through 12, and `20260725*` adds careers, intake import, the Agent 6 Vault helpers, and the `dash` schema. New migrations sort after those.

**A column the client computes cannot be sorted.** The candidate list's Requisitions column was assembled in the browser from a second and third read (`applications`, then `requisitions`), so Postgres had nothing to order by and a sortable header would have silently re-run the default sort. `20260910000002_candidate_list_requisition_codes.sql` moves the aggregate into `candidate_list` as `requisition_codes`, a correlated `string_agg`. **Measured before writing it:** an unfiltered sort over 73,023 candidates and 86,163 applications is 210.734 ms using `idx_applications_person` and `requisitions_pkey`, and the default list load pays nothing because `CANDIDATE_VIEW_COLUMNS` does not select the column and Postgres prunes an unreferenced subquery out of a simple view (`Execution Time: 0.771 ms`). The page still builds its displayed chips from its own read, because that read also feeds the CSV export; dropping the client join is a separate change and would simplify `exportFilteredRows` considerably.

`app/src/lib/database.types.ts` is **hand-derived** from the migrations, not generated. It holds all 24 tables (Row/Insert/Update), the 12 enums, the locked stage-order arrays (`REQUISITION_STATUSES`, `APPLICATION_STAGES`, `DEAL_STAGES`, `TICKET_STATUSES`) and the jsonb shapes for `people.emails/phones/education`. If a migration changes a table, change this file in the same edit. Stage sets are locked: do not reorder or extend them.

### The Supabase client

One client, `lib/supabase.ts`, imported directly everywhere. `database.types.ts` carries `Relationships: []` on all 25 tables, which is what postgrest-js needs to keep Insert and Update payloads from collapsing to `never`.

Four module-local `db.ts` shims used to work around that missing field. They were reduced to one-line re-exports once the types were fixed, and were deleted on 2026-09-02. `modules/dashboards/db.ts` survives for one reason only: it exports `dashDb`, the same client scoped to the `dash` Postgres schema. Use `dashDb` for `dash` views and `supabase` for everything else.

### Frontend structure

**`integration_settings_write` lets an admin write anyone's row**, which makes a test cleanup a footgun. The policy is `get_my_role() = 'admin' OR staff_id = auth.uid()`, so `delete().eq('key', 'ui.recentlyViewed')` issued as the admin persona deletes that key **for every staff member in the database**, not just the persona's own. Four spec fixtures did exactly that and quietly wiped real accounts' Recently Viewed rails and dashboard section preferences on every suite run. Always scope such a delete with `.eq('staff_id', <the signed-in id>)`; `deleteOwnSettings(persona, keys)` in `tests/env.ts` is the only way to do it, and it throws rather than guess if it cannot resolve the id.

**Per-staff UI preferences live in `integration_settings`, not in a new table.** That table is a staff-scoped key/value store by its own migration header, and its RLS already resolves `staff_id = auth.uid()`, so `hooks/useSectionPrefs.ts` writes keys like `ui.sections.dashboard.myview` with `value` of `{"hidden": [...]}`. Two things to know before using it: `uq_integration_settings_staff_key` is a **partial** unique index (`where staff_id is not null`), and Postgres cannot use a partial index for `ON CONFLICT` inference through PostgREST, so read the row id and branch to update or insert rather than calling `upsert`. **Corrected 2026-09-10:** this said `useRecentlyViewed` keeps its list and item limit in `localStorage`. It does not, and has not for some time: it reads and writes `integration_settings` under `ui.recentlyViewed`, with no `localStorage` path at all, so the rail follows a person between browsers and a Playwright context starts with whatever that staff row already holds. Recorded as decision 0005 in the second brain.

**`.fo-page-head` is the sticky, opaque page header wrapper**, holding the title row plus the search box and buttons. A record page renders its action bar **once**, inside it.

`.fo-page-toolbar` is the sticky band under it, and **`flush` on `ListPage` is what joins the two**: without it `.list-page:not([data-flush='true']) > .fo-page-toolbar` adds a top border and a canvas-coloured shadow, so the toolbar reads as a separate box. That, not any missing `position: sticky`, is why the candidate list's search row looked detached while the requisition list's did not.

Bulk action buttons belong in `bulkBar` with `bulkBarOpen`, which grows `.fo-page-head-grow` from `0fr` to `1fr` inside the sticky head. Buttons that are permanently visible but disabled were the old shape; the new one is that they do not exist until a row is ticked, so a test asserting `toBeDisabled()` on them has to become `toHaveCount(0)`.

**A list search runs only when it is submitted.** Klent's call, 2026-09-10: *"i don't want the table results to filter everytime i type a letter. it should only change results if i click magnifying glass icon or hit enter."* `useSubmittedSearch()` in `lib/quickSearch.ts` returns `input`/`setInput` for the box and `term`/`submit` for the query, both seeded from `?search=`; every list page binds the box to `input` and filters on `term`. **This replaced the 2000ms debounce on the requisition list**, which was an earlier request of his and is now redundant: a debounce is a guess at when typing has stopped, and submitting says so. Suggestions still run on their own 300ms debounce while you type, and submitting dismisses them. A test that fills a list search box and expects the table to narrow must press Enter; `searchList(page, name, term)` in `tests/e2e/helpers.ts` does both.

**Every search box has a clear button** when `onClear` is passed. `[data-clearable='true']` insets the input by 30px for the X; `[data-inset='true']` (set when there is no `trailing`) adds the submit glass, moves the X to `right: 30px` and widens the inset to `calc(var(--control-h) + 30px)`. So the list toolbar and the utility header get X-then-glass at 62px of padding, and `/search`, which supplies its own Search button, gets the X alone at the right edge with 30px. Clearing empties the box, re-applies an empty term so the list actually resets, cancels any pending suggestion fetch, and puts the cursor back in the box.

**The sidebar Quick Search has no input of its own.** It was a per-module keyword box (plus, until the same day, a First/Last Name pair) that navigated to `<list>?search=<term>`, which is what the list toolbar's own box does better: in context, with suggestions, a clear button and submit-only filtering. **`TableColumn.align: 'center'`** puts a `cell-center` class on both the `th` and the `td` and centres the sort button with it. Icon-only columns want it; the candidate Resume column is the first user.

**`.info-grid`'s label columns are fixed at 160px and 192px, and that is load-bearing.** They were `max-content`, which resolves **per grid**: once Candidate Information was split into groups, the Name group computed `65.9px … 74.5px` and the Location group `49.8px … 120.1px`, so no label lined up with any other and the section read as ragged. A `display: contents` row cannot borrow its parent's tracks, so grouped label/value grids need a fixed label width. The 192px on the third column is 160 plus the old `nth-child(even) > dt { padding-left: var(--sp-4) }` gutter, which that hack could no longer create once the column stopped growing to fit.

**`.record-section-body { gap: 16px }` is shared by every record section and must not be removed.** Klent's rule, stated twice on 2026-09-10 after an experiment removing it: *"do not remove gap as it affects other components."* It also means a **group inside a section adds no spacing of its own** — `.info-group` carries no margin, no padding and no rule, because the section gap already separates it from its neighbour. Adding 8px of margin plus 8px of padding on top of the 16px gap is what made the groups read as unevenly spaced. The rhythm is 16px between groups from that one rule, 8px from a group label to its grid, 4px between grid rows, and `candidate-record.spec.ts` C9 asserts every gap between groups is the same number and that a group's own borders are `0px`.

**The calendar icon lives inside the date field**, one border around the pair with a borderless input and a borderless button, and `DateField` has always had the icon. That treatment existed only as four `.fo-qs-advanced-section` overrides for the filter rail; it is now the default on `.date-field-row` and those overrides are deleted. Reach for `DateField` rather than building a date input, and if a variant looks wrong, check whether the wanted style is already an override somewhere before adding another.

**`TableColumn.width` is only a hint; `minWidth` is the one that holds.** `.table` is `table-layout: auto`, so a specified `width` on a `th` loses to the auto algorithm whenever other columns want the space: the candidate Location column was set to `width: '200px'` and still measured **106px**. `minWidth` is respected. `nowrap` is the other lever, and it is safe here because `.table-wrap` is `overflow-x: auto`, so a wide table scrolls in its own box and the document does not (`phone.spec.ts` holds that line).

**Do not skeleton the search row.** A `headLoading` prop that swapped the toolbar for a skeleton bar was built and removed the same day, 2026-09-10, on Klent's instruction: *"don't dispolay a sekeleton to the searchbox line."* `useMinimumVisible(loading)` is also true while someone is typing in that box, so the skeleton takes the control away mid-keystroke; and the title, description and breadcrumb trail are all known at first paint anyway. The table is what loads, so `.fo-skeleton-card` around a `Skeleton rows={8}` is the whole loading state a list page needs.

A control rendered in `ListPage`'s `actions` prop can open the filter rail through `useListPageFilters()` from `components/ui/ListPage.tsx`, which also focuses the first column checkbox on request. Before that context existed the two column gears could only tell the user where the picker was.

### Styling

**Stacking order is a named scale, not a number you pick.** Thirteen `--z-*` tokens in `tokens.css` carry the values that were already in use, so the whole order reads in one place: `--z-raise` 1, `--z-sticky` 2, `--z-page-toolbar` 8, `--z-action-bar` 10, `--z-menu` 40, `--z-overlay` 50, `--z-overlay-module` 60, `--z-toast` 70, `--z-dialog` 100, `--z-field-layer` 130, `--z-utility-hint` 300, `--z-recent-settings` 400, `--z-boot` 500. Naming them exposed a real inconsistency that has **not** been changed, because changing it is a visual decision: the four modal overlays sit at three different levels (`.rq-overlay` 50, `.intake-drawer-overlay` and `.sales-modal-overlay` 60, `.fo-dialog-overlay` and `.fo-placeholder-overlay` 100), and `.fo-action-menu` at 40 is **below** all of them, so an action menu can never open above a dialog. `.field-select-menu` and `.date-dialog-layer` at 130 are above everything on purpose, because a select inside a dialog has to escape it.

`styles/tokens.css` holds the design tokens verbatim from the architecture doc and is the only file that defines custom properties. Everything else lives in **cascade layers**, and `styles/app.css` is now nothing but the layer order: fourteen `@import './layers/<name>.css' layer(<name>)` lines followed by one `@layer` statement that also declares the five `module.*` layers. Layer order is `base, shell, auth, controls, tables, pages, panels, narrow, taleo, states, pagination, motion, widgets, print`, then the modules.

Two consequences worth knowing before editing CSS:

- **An unlayered rule beats every layered rule, whatever its specificity.** One stray rule outside a layer silently outranks the entire stylesheet. `node scripts/check-css-layers.mjs` fails the build on that, and on a layer file that is not imported or that declares its own layer.
- **Across layers, layer order decides and specificity does not.** A more specific selector in an earlier layer is dead, not stronger. **Find the layer of the rule you are overriding before you write the override**: this was got wrong four times on 2026-09-14 (QA-071), including a dialog width class that had been silently doing nothing while every dialog marked `wide` rendered at the base width. When an override is needed at all, prefer sharing the component: the requisition edit dialog stopped needing any override once it rendered the same `FormSections` as the other edit dialogs. A module rule now beats a shared rule even when the shared one is more specific, so the fix for a conflict is to move the rule to the right layer rather than to add a class to the selector.
- **Within one layer, a later single-class rule beats an earlier one.** `.fo-scroll-shade { position: relative }` was appended to `controls.css` after `.field-select-menu` (fixed) and `.fo-action-menu` (absolute), so it silently unpositioned every dropdown and they fell into the document flow. A utility class must not set `position` unless every element that will carry it wants that position.
- **`overflow-y: auto` makes `overflow-x: visible` compute to `auto`.** Capping a menu's height therefore gives it a horizontal scrollbar unless you also write `overflow-x: hidden`. Say it out loud on every scroller.
- **A `position: sticky` child is clamped to its containing block**, which for a flex item is the flex container's *content* box. So a sticky overlay cannot reach into the scroller's own padding, and no negative margin will move it there: the flow position shifts, then the clamp puts it back. A scroller that wants an edge-to-edge fade must carry **no vertical padding** at all, with the spacing moved onto its rows (`.checkbox-list > *:first-of-type`). `.fo-scroll-shade` depends on that. `tests/e2e/scroll-shadow.spec.ts` used to assert the padding was zero and was **deleted on 2026-09-14** along with three other specs that only measured CSS; the constraint is still real, so check it by hand when you touch a shaded scroller.

`import './styles/app.css'` must stay the **first** import in `main.tsx`. It is not cosmetic: the intake module's stylesheet reaches the entry bundle through `useIntakeBadge` in `PrimaryNav`, and if it is emitted first then `module.intake` becomes the document's first-declared layer and the whole order inverts.

No CSS framework and no charting library (dashboard bars are hand-rolled CSS in `dashboards/components/BarList.tsx`). Use the token variables; never hard-code a color. Inter with Roboto fallback, 8px grid, 12px cell padding, max shadow `0 1px 2px rgba(0,0,0,.05)`.

**15** things bite anyone adding tests here. **Corrected 2026-09-10:** this line read "Eight" and had not been updated when the callback-ref item was added; counted with `grep -cE '^- \*\*'` over the block.

- **`accessibility.spec.ts` is in scope for every markup change, whatever else you ran.** It walks each route with axe, so a change nowhere near it can still break it. `3335827` shipped `aria-hidden-focus` on `.fo-page-head-grow`, a closed bulk bar a keyboard could still tab into, and it reached CI because that run was scoped to the specs that had been edited. Scope a local run to the changed specs for a CSS tweak; run the whole browser suite (about 6 minutes at `FOOS_PW_WORKERS=4`) before any commit that changes markup. That is not the visual audit harness, which lives in `tests/audit/` and is a separate, much slower thing.
- **To assert that something animated out, record it, do not look for it.** Four sites in `interaction-motion.spec.ts` (**deleted 2026-09-14**) clicked a dismissal and then read `!!document.querySelector(...)` to prove the node outlived the click. On a 2 vCPU runner the 140ms exit finishes before the CDP round trip lands, so the node is already gone and the assertion reads `false`. `watchOverlayExit(page, selector)` in `tests/e2e/helpers.ts` installed a `MutationObserver` on `data-closing` **before** the click and returned a reader for **after** `toHaveCount(0)`. It went with its last caller on 2026-09-14, and `knip` failed the CI `frontend` job on the orphaned export; if you reintroduce the pattern, reintroduce the helper with it. History is machine-independent; a sample of the present is not.
- **Adding tests re-shards the suite, which changes who runs next to whom.** `--shard` splits by test count, so two new tests in one file move the boundary and give every later file a different set of concurrent neighbours. On 2026-09-11 that alone turned `record-ui.spec.ts`'s Recently Viewed test red: it passed alone and in the old shard 2, and failed in the new one because a neighbour signed in as the same `recruiter` persona wrote the same `integration_settings` row and evicted one of its two records. The fix is the documented one taken further: the test seeds `{ items: [], limit: 50 }` for that persona in `beforeEach`, so no neighbour's opens can push its own records out of the window it measures. **A per-persona row is shared state; give your assertion room rather than assuming you are alone in it.**
- **A motion assertion must read what the rule declares, not what the animation happens to be showing.** CI is 2 vCPU against this machine's 10, so any single sample taken "during" a 150ms transition lands wherever the runner got to. Two failures on 2026-09-11: `candidate-record.spec.ts` C11 polled until the highlight *stopped changing*, and on CI two consecutive frames read the same mid-fade `rgba(240, 246, 251, 0.96)`, which looked settled against the local `rgb(240, 246, 251)`; `interaction-motion.spec.ts` R7 (since deleted) read the closing menu's opacity and got `0`, because by then the exit had finished. Poll for the **token** (`getComputedStyle` on a probe with `background-color: var(--fo-option-hover)` gives the exact target string) or assert the **declared** `animationDuration`/`transitionDuration`, never a sampled intermediate value.
- **That rule applies to rows you seeded by hand, too.** `intake-list.spec.ts` was written against 130 demo intake rows seeded for Klent to look at, and passed. The rows were then removed as sample data and **six of its fifteen tests failed**, on a database CI never had those rows in either. A spec seeds what it needs in `beforeAll`, marked so `afterAll` can remove it: `intake_items` has no `is_test` column, so the fixture is tagged with a run-unique `batch_label` and deleted by it.
- **A test may not assume a row it did not create.** This is the one that keeps reaching CI. This checkout's local stack holds the **Zoho copy: 73,024 candidates and 690 requisitions**. CI runs the suite against `supabase db reset`, which is migrations plus `seed.sql` plus the four personas and **nothing else**, so a list page there has single digits of rows. Three tests asserted things only a large database makes true and passed locally by construction: `quick-search.spec.ts` Q14 expected exactly **20** rows after clearing a search, Q10 typed the literal `man` and waited for suggestions, and `candidate-record.spec.ts` C7 expected `Next candidate by name` from a "cold" URL that on a small database is a history entry React Router can restore siblings state from, because the fixture lands on page one of the list. Running the browser suite locally, any number of times, cannot surface any of them. Derive the expectation from the page (`const unfiltered = await rows.count()`), take search terms from a row the list is already showing, and open a genuinely cold URL in `context.newPage()`. `bash scripts/ci-parity.sh snapshot | run | restore` is the way to actually reproduce CI here: it pg_dumps the local database, resets it to CI's shape, runs the suite and restores. It is destructive between `run` and `restore`, so read it before using it.
- **Fixtures must be run-unique.** Cleanup by a shared prefix means two specs delete each other's rows. Every spec derives its tag from `process.pid` plus a random suffix.
- **`datetime-local` inputs are local time.** Filling one from `toISOString()` puts the value hours out; on UTC+8 a "+1 hour" reminder lands in the past and the reminder sweep fires it. Use `localDateTimeValue()` from `tests/e2e/helpers.ts`.
- **A local run stops at the first failure; CI reports them all.** `tests/playwright.config.ts` sets `maxFailures: Number(process.env.FOOS_PW_MAX_FAILURES ?? 1)` and defaults `workers` to **4**, which was measured safe. Klent's complaint on 2026-09-11 was that a run took minutes "just to encoutnre a fucking error", and it did: the suite, 339 tests at the time and 312 now, ground on past the failure. CI sets `FOOS_PW_MAX_FAILURES: '0'` because a push that reports one failure per run costs a round trip per defect, which is what made the 2026-09-11 CI sequence so long. Raise it locally with the same variable when you want the whole picture.
- **Playwright is capped at 2 workers** because the local Realtime container has a messages-per-second limit and every page subscribes. Symptom is `docker logs supabase_realtime_* | grep MessagePerSecondRateLimitReached` and live-update tests going stale. **Measured 2026-09-10:** the cap is softer than it reads. `FOOS_PW_WORKERS=4` ran **263 passed at 4.4m, 4.5m and 4.6m** on three consecutive passes against 8.5m at two workers, and the rate limit fired 25 times without failing anything. Use it locally. What four workers *does* expose is shared per-persona state: `record-ui.spec.ts` asserted the Recently Viewed rail read exactly `["Candidate", "Company"]` and got `["Candidate", "Candidate"]`, because the rail lives in `integration_settings` under `ui.recentlyViewed` and every worker signed in as `admin` writes the same row. An assertion about a per-persona row must describe only the records that test created. **Do not raise it in CI:** `ubuntu-latest` on a private repo is 2 vCPU against this machine's 10, and CI is already about twice as slow per test at the same worker count, so more Chromium workers would contend rather than parallelise. **Done 2026-09-10: the CI job is sharded two ways** (`strategy.matrix.shard: [1, 2]`, `--shard=${{ matrix.shard }}/2`), each shard keeping 2 workers and its own Supabase stack, with the vitest step gated to shard 1 so it is not paid for twice. Two shards, not three: sharding always costs more billable minutes than it saves in wall clock, and two buys about half the wall time for about 20 percent more minutes where three buys a bit more wall time for 40 percent. `npx playwright test --shard=1/2 --list` is how to check the split stays balanced.
- **Vitest runs files serially** (`fileParallelism: false`) because the 10 MB oversized-resume case saturates the edge runtime enough that concurrent Edge Function calls return 503.
- **A flat wait or a single read is never a substitute for a condition.** This cost four separate false failures on 2026-09-07 alone, logged as QA-019, QA-021 and QA-022: a combobox read once while its two neighbours polled; `waitForAnimations` returning at its 3000ms cap indistinguishably from success; a lookup list measured before its query landed; and a layout measured 1200ms after navigation because 1200 felt long enough. Every fix had the same shape, and none of them was to wait longer: **assert the condition, or read until the reading stops changing.** `optionNames`, `chooseOption` and `settleLayout` in `tests/e2e/helpers.ts` and `phone.spec.ts` are the patterns to copy. A wait that can give up must not return the same way it returns on success.
- **`Element.closest()` matches the element itself.** `phone.spec.ts` filtered overflow culprits with `el.closest('.table-wrap')` to skip a scroll container's contents, and thereby skipped the container too, so the one element most likely to be at fault was the one never reported. Use `!el.matches(sel) && el.closest(sel)` when the intent is descendants only.
- **Never write `.click().catch(() => undefined)` in anything that classifies an outcome.** The Goal 8 sweep did, and one overlay with a full-screen backdrop turned into **17 fabricated dead controls per page**: every later click threw `intercepts pointer events`, the catch discarded it, and the default outcome said the control did nothing. Fixing the harness alone moved the admin shell from 17 dead to 1 and the dashboard from 17 to 0, with no application change. Record a swallowed click as its own outcome, and hash the output images: **15 byte-identical PNGs** were the only visible symptom, because no product opens fifteen modals that render identically. `pressAndRecord` in `tests/audit/sweep-lib.ts` is the shape to copy.
- **A callback-ref hook must tear down in the ref, not in a cleanup-only effect.** `main.tsx` wraps the app in `StrictMode`, so React runs every effect, then its cleanup, then the effect again. `useScrollShadow` kept `useEffect(() => () => detach(), [])`, so that second pass removed its scroll listener and nothing put it back: the ref callback is not re-invoked when the DOM node has not changed. The flags froze at their mount-time values, which read as a permanent bottom fade and a top fade that never appeared. Scrollers that happen to remount when their data lands (the recent list, an opened select) hid the bug; a dialog list that mounts once exposed it. Detach in the ref, which React calls with `null` on unmount, and the double pass is symmetric.
- **A global `keydown` listener cannot express a dismissal contract.** The first fix for QA-024 added Escape-to-close on `window`, which dismissed *every* open overlay at once and detached the date-field trigger out from under `date-field.spec.ts` (`element is not stable`, then `element was detached from the DOM`) because that trigger lives inside the filter rail the same Escape closed. The APG wording is *"Close the menu that **contains focus**"*, singular. Scope the listener to the overlay's own subtree, check `event.defaultPrevented`, and `stopPropagation` so no outer scope also acts. `useDismissable`'s optional `escapeScope` ref is that shape.

Teardown belongs in `afterEach`/`afterAll`, never inline at the end of a test: a failing assertion aborts the rest of the block and the rows leak. Delete a storage object **before** its `attachments` row, or the file becomes unreachable (the DELETE policy matches on that row and `remove()` then returns an empty array with no error).

Four migration and repair tools, all of which refuse a non-local target unless `--allow-remote` is passed, and all of which dry-run by default:

```sh

node scripts/add-legacy-owners.mjs                     # inactive staff rows for Zoho owners with none
node scripts/backfill-zoho-candidate-fields.mjs        # repairs star_grade and initial_date from the export

```

The importer resolves paths relative to the current directory, so **run it from the repository root**; from inside `migration/` it writes its report to `migration/migration/out/`, and those reports contain candidate data.

**This checkout is linked to the live project.** `supabase/.temp/project-ref` holds `hilieyehhecrlccdveta`, so every `--linked` command targets production. **Decided 2026-09-14: there are two environments and only two**, a developer's local stack and the Cloudflare Pages site on that project. No staging, no develop project, no preview environment. Supabase is on **Pro**; the host is **Cloudflare Pages**, assets only. **Corrected 2026-09-09:** relinking needs `supabase link --project-ref <ref>`, not just writing that file, because `db.<ref>.supabase.co` is AAAA-only and the CLI otherwise answers `LegacyDbConfigIpv6Error`. Bulk work must use the **session pooler on 5432**; the transaction pooler on 6543 breaks `pg_dump`.

Develop against the local stack: `supabase start`, then `npm run db:reset` (which also seeds the four test personas and restarts the edge runtime, since `db reset` otherwise leaves it holding stale connections to the storage container it just replaced and every upload fails with `StorageApiError 502`).

`npm run db:push` is deliberately gated behind `scripts/confirm-production-push.mjs` and exits 1. Two reasons: it writes to the live project, and the migration ledgers do not line up. Ten migrations were applied to production through the MCP connector on 2026-07-25 under generated timestamps, while the repo carries six hand-written files reconstructing the same objects under different names. `supabase db push` refuses on its own with `LegacyDbPushMissingLocalError`; do not "fix" that with `migration repair --status reverted` without reading the Deployment state section of `docs/environments/`.

Every demo row carries `is_test = true`.

**There are exactly four test accounts, one per role**, and they are the only accounts either suite signs in as: `foos.admin@`, `foos.recruiter@`, `foos.sourcer@` and `foos.bd@ventvest.com`, on staff ids `a0000000-…-0005/0002/0003/0004`. **Rewritten 2026-09-14.** There used to be two overlapping sets: Rita/Sam/Ben seeded here plus a separate `foos.*` set added by hand through `scripts/add-local-staff.sql`, and **no admin row at all other than John**, which is why `personas.sql` hung the `demo-admin@ventvest.test` login on John's id. An admin test session therefore wrote as John Buena, `john@ventvest.com` could not sign in, and running `personas.sql` against the live project would have overwritten his real Google identity. Logged as QA-064. The Rita/Sam/Ben rows were **renamed rather than deleted**, keeping ids `…0002/3/4`, because seed data references those ids 33 times as owners; deleting them would have cascaded that data away.

**Nothing resets these passwords by accident, and that is verified rather than assumed.** The Cloudflare deploy is assets-only (`wrangler.jsonc` carries an `assets` block and no database binding); `migration/import.mjs` has zero references to `auth` or to staff credentials; `add-legacy-owners.mjs` only inserts inactive `legacy+…@import.invalid` rows. The single path that writes them is `npm run db:reset` → `post-reset.mjs` → `personas.sql` → `sync-test-accounts.mjs`, and every step reads the same configured value, so a reset restores the four accounts unchanged. `scripts/rotate-persona-passwords.mjs` **was deleted**: it minted a different random password per persona and printed it once, which is exactly how the four values drifted apart and stopped working on both stacks. Use `node scripts/sync-test-accounts.mjs` instead; it works from an allowlist of those four emails, refuses any account whose `auth.users.id` does not match its `staff.id`, dry-runs by default and needs `--allow-remote` for the live project. The purge order is `people`, `requisitions`, `deals`, `companies` (README.md has the statements). Because all seeded requisitions are `is_test`, the live careers listing correctly shows zero roles.
